# Rebuild sequence — full reference

The long form of the **Rebuild** section in `AGENTS.md`: the raw command chain
the rebuild grew out of, the three implementations of it and where they
deliberately differ, the Flatpak and Antigravity probes, the flag semantics,
and the measured costs the flags are chosen on. Read it before changing
`pkgs/preflight/`, `users/mj/rebuild-classic.nu` or `scripts/rebuild-classic.sh`.

**Startup authorization.** Every real rebuild authenticates before SSH key
loading, checkout sync, updates or cleanup, and before Preflight starts its TUI.
`PREFLIGHT_PRIVILEGE_TOOL` selects `auto` (the default), `sudo`, `doas` or `run0`;
auto tries those helpers in that order and keeps the selected helper throughout
the run. `sudo -v` validates credentials; doas and run0 use a privileged `true`
because [doas](https://man.openbsd.org/doas.1) has no portable validate-only flag
and [older run0 releases](https://www.freedesktop.org/software/systemd/man/latest/run0.html)
do not support `--validate`. The doas/polkit policy must permit this `true` probe
as well as the maintenance commands; permission for `nixos-rebuild` alone can
leave the probe unauthorized. Passwords and fingerprint authentication stay with
the helper. No password is read or stored by Preflight, and no keep-alive changes
the configured lifetime. Later steps may prompt again after expiry or when
doas/polkit policy does not retain authorization. Without terminal input,
authentication uses `sudo -n -v`, `doas -n true` or
`run0 --no-ask-password true`, failing promptly if authorization is needed.
Preflight reports an authentication refusal with exit 4 before maintenance.
`--dry` builds run `nixos-rebuild dry-build` without escalation; read-only
subcommands and help also skip authentication. Both deprecated rebuild scripts
follow the same selection, startup timing and dry-build behavior. With doas or
run0, the TUI is suspended for each entire privileged command, including the
rebuild, even when authorization is cached. Output and any prompt appear in the
normal terminal until that command exits.


Targets `steelbore-thinkpad` (stable; march pinned to v3 in `hosts/thinkpad/`). Stages `/etc/nixos/` from the working tree, garbage-collects, wipes `/tmp`, vacuums journal, checks disk, then rebuilds. Run as the user, not as root.

```nu
# Nushell
cd /spacecraft-software/bravais/ ; gitway-add ~/.ssh/<signing-key> ; nix flake update antigravity-nix construct gitway ; sudo nix-collect-garbage --verbose -d ; sudo rm -r /tmp/* ; sudo journalctl --vacuum-time=7d ; df -h / ; sudo cp --verbose -r ...(glob /spacecraft-software/bravais/*) /etc/nixos/ ; print "cd /etc/nixos/" ; cd /etc/nixos/ ; sudo rm --verbose -r ...( [v0 "*.md" "flake.*" LICENSE "*.docx" hosts lib modules overlays users "*.txt"] | each { |p| glob $p } | flatten ) ; cd /spacecraft-software/bravais/ ; sudo nixos-rebuild switch --flake .#steelbore-thinkpad --show-trace --verbose
```

**`preflight` (Rust, `pkgs/preflight/`) is the supported entry point** and the one to reach for. It accepts every flag the two older shells do and adds `--no-commit`, `--reclaim`, `--gc-all`, `--journal-days <DAYS>`, `--mcp-deploy`, `--update-vendored`, `--update-ai-tools`, `--update-appimages`, `--no-appimages`, `--update-flatpaks`, `--tui` / `-E` (`--format explore`), `--cli` (`--format human`), `--accessible` / `--no-accessible`, `--no-notify`, `--term-protocols <LIST>` and `--json`; `preflight disk report --json` is the machine-readable free-space surface, and `preflight schema` / `preflight describe` emit the command surface for an agent. Both older paths — the Nushell `rebuild` and `scripts/rebuild-classic.sh` — now open with a deprecation question that aborts unless answered `y`, with `--yes` as the escape hatch, so choosing them is deliberate rather than habitual. `preflight` deliberately wraps **none** of the tools it drives (`nixos-rebuild`, `nix`, `sudo`, `rsync`, `vacuum`, `gitway-add`, `mcpctl`, `flatpak`, `nu`, `git`, and under `--update-ai-tools` every AI tool's own updater) onto PATH — pinning them into its closure would freeze `vacuum` and `mcpctl` at whatever revision it last built, which is exactly the drift its own mcpctl probe exists to report (same reasoning as constraint #23).

**Each run brings the checkout up to date with `origin`; non-dry runs authenticate first**, in all three implementations (`pkgs/preflight/src/git_sync.rs` carries the reasoning; `bravais-git-sync` in `rebuild-classic.nu` and `git_sync` in `rebuild-classic.sh` mirror it). Until 2026-10-19 the rebuild built whatever `/spacecraft-software/bravais` happened to hold and never touched git, and that bit twice in one day: Margo was "missing" after a rebuild because the checkout sat on a PR branch that had been merged and deleted days earlier, and a PR test would have silently built `main` because nothing had switched to the PR branch. The policy, in order: (1) uncommitted changes to tracked files are **carried along** (the way `git switch` and `git merge --ff-only` carry them) and named in a warning, and the run is refused (`DIRTY_TREE`) only when the incoming commits touch them too. Refusing on any dirt was the first design, and on its first live run it refused the very next run: preflight's own updaters left `flake.lock` and the vendored pins modified, so a dirty tree was the normal state between a rebuild and the deps commit that recorded its bumps (since 2026-10-24 a clash with the incoming commits is no longer a refusal either: edits to files the incoming commits touch are stashed and reapplied after the move, and a reapply that clashes leaves the incoming version built and the edits in `git stash` — `git_sync::Clash`; a local-only branch already merged into the default branch returns to it; and `preflight` makes that commit itself — see **Deps commit** below — but the two shells, a PR branch, `--no-commit` and a failed switch still leave them); (2) `git fetch --prune origin` (`FETCH_FAILED` if it cannot; pruning is what makes a deleted upstream visible as gone); (3) the branch is `--branch <name>` if given, else the current branch while its upstream exists, else -- detached `HEAD`, or an upstream merged and deleted -- origin's default branch; a local branch that never had an upstream is refused (`NO_UPSTREAM`), because it is deliberate local work; (4) fast-forward only -- local commits origin lacks are refused (`NOT_FAST_FORWARD`), never merged or reset. When the incoming commits also change `flake.lock` and the local copy carries the last run's uncommitted bump, the bump is dropped if a flake update follows (it is about to be redone) and refused (`LOCK_CONFLICT`) under `--no-update`, where the lock is what gets built. Refusals stop the run before anything is built; `preflight` exits 5 for these conflicts, 3 for `NO_SUCH_BRANCH`, 1 otherwise, each with a runnable hint (the Nushell `rebuild` raises an error instead, since `exit` in its interactive form would close the shell). Under `--dry` the sync fetches and reports what it would do, refusals included, but never moves the checkout. `--no-sync` builds the tree exactly as it is (an uncommitted experiment, or offline); `--branch` / `-b` switches to origin's branch first (an `origin/` prefix is accepted), creating a tracking branch if there is no local one, and is validated before it reaches git (no leading `-`, whitespace, control characters or `..`). The signing key (`gitway-add`) is now loaded before the fetch rather than before the flake update, so it also runs under `--no-update` unless `--no-sync` is given too. `nixos-rebuild` builds the flake from the git tree, so a checkout that is not where the user thinks it is would otherwise be invisible until something is missing after the switch.

`nix flake update construct` is the *first half* of `skills-sync`, which also builds the new tree and moves the skill pointer, so no rebuild is needed to apply it — see `docs/skill-pointer.md`.

The whole sequence above is also wrapped as `rebuild` — **one** implementation in `users/mj/rebuild-classic.nu`, wired up in `users/mj/shell.nix` both as a Nushell `def` embedded in `config.nu` and as a real `rebuild` binary (a `#!nu` script over that same file), so every shell has it and not only Nushell. A `nu` script invoked that way does not load `config.nu`, which is why `rebuild-classic.nu` must carry its own helpers. It differs from the raw chain in three deliberate ways: GC keeps a week of generations (`--delete-older-than 7d`, not `-d`); the update bumps every input rather than the raw chain's three, so `unstablePkgs` never lags stable (plan 5.2) and a new input needs no edit, and a monthly nag reminds to run `nu pkgs/update-vendored.nu --check` (vendored-binary bumps, plan 5.1); the `/tmp` wipe is dropped (builds use `/mnt/nix-tmp`, and `rm -r /tmp/*` can kill an X11/LeftWM session); and the `/etc/nixos` step is a lean `rsync -av --delete --delete-excluded` mirror (tracks deletions, prunes stale files; excludes `.git/`, `result`, `.claude/`) that runs only after a successful switch. The deprecated `rebuild` implementations still update the declared Flatpaks, **last**, after the switch, and **detached**; supported `preflight` does so only with `--update-flatpaks`, `--detach-flatpak`, or `--full-update`. `services.flatpak.update.onActivation` is the more obviously declarative spelling and is deliberately NOT used: it blocks activation on an unbounded download (a browser is ~150 MB, a runtime bump ~250 MB, and the full set measured 4.4 GB at ~0.4 MB/s ≈ three hours), and a switch held open for hours — or interrupted part-way — is a worse failure than a Flatpak being a few days old. Running it inline after the switch was the first shape and carried the same cost minus the half-applied-system risk; detaching is what removes the wait. These entries pin no version anyway, so "current" is a property of the remote, not of this flake. The weekly timer in `modules/packages/flatpak.nix` remains the safety net for stretches without a rebuild.

Four Nushell commands back it, defined beside the `skills-*` ones: `flatpak-status` (a record — refs still outdated, whether an update is running, free space, log tail, and the tail parsed into `parsed`), `flatpak-update` (starts a detached update via `setsid --fork`, writing to `~/.local/state/flatpak-update.log`), `flatpak-watch` (follows a running update with a progress bar until it ends, then returns `flatpak-status`), and `flatpak-log` (that path, fixed so all of them share one log). `preflight flatpak status` and `preflight flatpak watch` are the same pair in Rust, with `--json` (`watch` off a terminal blocks until the update ends, then reports — the shape an agent wants). Three non-obvious details are encoded there: the log is split on `\r` as well as `\n` before reading, because older Flatpak releases redrew their progress bar in place and the file was then one enormous line that reads as frozen; the running check matches the **command line** — argv[0] `flatpak` (or `.flatpak-wrapped`) with an `update` argument — because `flatpak-session-helper`, `-portal` and `-system-helper` are always-on daemons that share the name and would report `running = true` forever; and the watchers never ask Flatpak anything, they read its log.

**Live progress, TUI mode and authorization notifications (`pkgs/preflight/src/ui.rs`, `pkgs/preflight/src/notify.rs`).** Until 2026-10-19 the only way to see a Flatpak update's progress was to run `flatpak-status` again and again. Now all three implementations, at a terminal, **follow** the update they just detached: a spinner, the operation counter, a bar and Flatpak's own rate and time left, e.g. `⠹ flatpak 2/5  ███████░░░░░░░░░░░░░░░░░  29%  1.2 MB/s  00:30  (4m12s)`. The numbers come from the log. With stdout not a terminal, Flatpak's CLI drops its redrawn table and prints plain lines (`progress_changed_cb` in `flatpak-cli-transaction.c`): `Updating 2/5…` as an operation starts, then `Updating 2/5… ████▌  23%  1.2 MB/s  00:30` every update interval; the newest line of either shape decides, and a counter with no percentage yet is a new operation at 0%. The overall percentage counts each operation as an equal share, because Flatpak reports no transaction total and the per-ref sizes appear only in its terminal-only table. The update is still detached — `setsid` puts it in its own session, so Ctrl-C at the watcher, closing the terminal or the rebuild exiting stop only the watching (`preflight flatpak watch` / `flatpak-watch` resume it). `preflight` spawns `setsid` **without** `--fork` and keeps the handle: a spawned child is never a process-group leader, so `setsid` execs in place, the PID is Flatpak's own and the final step carries its exit status; it follows the update **last**, after the closing disk report, so the one wait that can run for hours holds nothing else up. `--detach-flatpak` returns at once instead, and every run that is not live always does: live means stdout and stderr are terminals, `TERM` is not `dumb`, and none of `AI_AGENT`, `AGENT` or `CI` is set (presence-based, as in `output.rs`). Off a terminal the output is byte-for-byte what it was. At a live terminal a rebuild run opens the full-screen TUI described below by default (since 2026-11-12; it also needs stdin to be a terminal and accessible mode off, and the subcommands never open it); `--cli` or `--format human` asks for line output instead, where `preflight` pins a **persistent bottom status bar** on stderr (`⠹ ████░░░░░░░░ 36% [4/11] 01:12 · update-vendored (3/11) · building .#ollama …`) across the entire run, piping each child's stdout and stderr above the bar and parsing sub-step progress (`[idx/total]` and `building .#<attr> …` / `[OK] built .#<attr>` from `pkgs/update-vendored.nu`). That default, or `--tui` / `-E` (or `--format explore`) — which differ only in that an explicit request warns when the TUI cannot open — is a full-screen `ratatui` TUI with a task checklist (side-by-side on terminals `>= 90` columns, stacked on narrower ones) showing ticks, per-step elapsed durations, an overall progress gauge and a scrollable live output pane (`j`/`k`, `Up`/`Down`, `PgUp`/`PgDn`, `g`/`G`, `f` to resume follow, `q` to close after completion). The alternate screen takes the run's output with it, so on closing the TUI writes a summary to stderr: one `[OK]` / `[SKIP]` / `[FAIL]` / `[STOP]` / `[----]` line per step with its duration and detail, followed by the last 40 log lines when a step failed (`exit_summary` in `ui.rs`), and ends with the path of the full log: every line of a TUI run is written, unbuffered and with escape sequences stripped, to `~/.local/state/preflight-last-run.log` as it arrives (the in-memory buffer keeps only the newest 2000), and the next TUI run truncates it. Passing `--accessible` (or `SPACECRAFT_A11Y=1`, or `NO_COLOR` / `TERM=dumb`; overridden by `--no-accessible`) disables cursor-addressed redraws and TUI mode and emits monotonic 10%-step linear announcements (`[PROGRESS] <task>: <pct>% - <msg>`). Whenever `preflight` waits longer than 400 ms on an authorization prompt (`sudo` password / `fprintd` fingerprint scan, or `gitway-add` SSH key passphrase — probed via `sudo -n true` first so cached credentials never flash a banner or leave the TUI alternate screen), `notify::AuthWatch` fires five best-effort notification channels and automatically dismisses/restores them as soon as authentication completes: (1) D-Bus `org.freedesktop.Notifications.Notify` via `busctl --user` (critical urgency, works across GNOME, Plasma, COSMIC, and via `dunst` on Niri, LeftWM and Margo; falls back to `dunstify -r 9919`), closed via `CloseNotification` on drop; (2) terminal bell (`\x07`) to `/dev/tty` (the only sequence sent on a bare Linux VT where `TERM=linux` has no `$ZELLIJ`/`$TMUX`); (3) `OSC 9` and `OSC 777` desktop notifications; (4) `OSC 2` window title prefix `[AUTH] …`; and (5) under Zellij (`$ZELLIJ` / `$ZELLIJ_SESSION_NAME`), badging both the hosting pane and tab title (`[AUTH: sudo] …`) via `zellij action rename-pane` and `rename-tab-by-id` and restoring them on drop. `--no-notify` suppresses all five channels. On the Linux console, or in a non-UTF-8 locale, the glyphs fall back to ASCII (`|/-\`, `#`/`-`), because the console font has no braille and no partial blocks.

**Terminal protocols (`pkgs/preflight/src/term.rs`, the `spacecraft-tui-protocols` skill).** `preflight` speaks three modern terminal protocols, each only where the terminal is known to handle it: **OSC 9;4** mirrors the overall gauge (and a standalone `preflight flatpak watch` percentage) into the terminal's tab or taskbar, shown as *paused* while an authorization prompt waits and briefly *red* when a step failed; the **kitty keyboard protocol** (flag 1, disambiguate) makes `Esc` exact in the `--tui` view; and **OSC 52** lets `y` in the `--tui` view copy the selected task (Tasks focus) or the retained log, newest lines first up to 74 000 bytes (Output focus), with a log line confirming what was sent, since terminals never acknowledge it. Nothing is sent, and nothing is probed, unless the run is *attended* (the same test as the live bar), `TERM` is set and is neither `dumb` nor `linux` — the kernel console prints an unknown OSC payload as text. At startup one write of `CSI ? u` (only with `--tui`), XTVERSION and a trailing DA1 goes to `/dev/tty` in raw mode, read with `poll(2)` under a 200 ms deadline and drained until the line is quiet for 20 ms (100 ms at most), so a terminal that answers nothing costs exactly the deadline and no reply reaches the shell. The probe runs only in the terminal's foreground process group (a background job would be stopped by `SIGTTOU`), and the signal handler is installed before it, so SIGTERM or SIGHUP during those 200 ms puts the saved terminal modes back before the process dies. Keys typed meanwhile are not lost: `--tui` replays them as its first input, and Ctrl-C, `Ctrl-\` and Ctrl-Z still raise their signals; outside `--tui` other keys are dropped, since a raw read cannot be pushed back. OSC 9;4 is **allow-list only**, never sent to an unknown terminal, because on many terminals `OSC 9` is a desktop notification and every update would pop one reading `4;1;50`: Windows Terminal, ConEmu, Ghostty, VS Code, Rio, contour, foot, iTerm2 3.6+, kitty 0.39+ (read from XTVERSION; kitty sets no version variable) and WezTerm builds dated 2025-02-10 or later — the 20240203 stable notifies instead, and the nixpkgs `0-unstable-YYYY-MM-DD` version is parsed for its date. Inside tmux, Zellij or GNU screen it is skipped, since the outer terminal is unknown. Every exit path restores in the skill's order — pop the keyboard flags, clear the indicator, leave the alternate screen, leave raw mode: the session's `Drop`, the panic hook, each suspension for `sudo` / `gitway-add`, and SIGINT / SIGTERM / SIGHUP, which a signal thread handles by stopping the drawer, restoring, then dying of the same signal so the exit status is unchanged. `--term-protocols=<list>` (`+name` forces on, `-name` off; names `keyboard`, `graphics`, `animation`, `clipboard`, `clipboard-rich`, `progress`, `pointer`, `all`) beats `SPACECRAFT_TERM_PROTOCOLS`, which beats detection; neither can open the gate for an agent, CI or a pipe. `--verbose` prints each protocol's state and reason, and `preflight describe --json` carries them under `terminal_protocols`. WezTerm answers `CSI ? u` only with `config.enable_kitty_keyboard = true`, and the reason line says so.

All three hand the flake update a GitHub token, because anonymously Nix resolves every `github:` input through the GitHub REST API at **60 requests an hour per IP**, and a bare `nix flake update` (every full run) exhausts that in one run -- 2026-09-27 died with `HTTP error 403 ... API rate limit exceeded` on `nixpkgs-unstable`; authenticated, the limit is 5000. The token is `gh auth token --hostname github.com`, read from the keyring on every run and passed as `NIX_CONFIG` = `extra-access-tokens = github.com=<token>` to the `nix flake update` child **only**: never written to a file (an `access-tokens` line in `~/.config/nix/nix.conf` would leave it in plain text), never into the store, never printed (`preflight` records a `github-token` step reading `from gh`, not the value). `extra-` appends rather than replacing any configured tokens, and an inherited `NIX_CONFIG` is kept. Without `gh`, or logged out, the update runs anonymously as before, with a one-line note. `pkgs/update-vendored.nu` is **not** covered: its release lookups are Nushell `http get` calls, which read no Nix setting.

After the flake update (full path only) it runs an `antigravity-status` probe -- see constraint #27 -- which warns if `antigravity-nix`'s pinned Antigravity IDE is behind what Google advertises, because bumping that input cannot move the pins inside it.

`scripts/rebuild-classic.sh` is the same sequence for a shell that is not Nushell -- an agent's tool shell, a rescue TTY, or a session where Home Manager has not been activated and the `rebuild` function therefore does not exist. It takes the identical flags and performs the identical steps -- including the `preflight` deprecation gate and its `--yes` escape hatch. There are now **three** implementations of this sequence -- `pkgs/preflight/` (Rust, the supported one), `users/mj/rebuild-classic.nu` (Nushell, one text serving both the `def` and the binary) and this script -- so **change one and change all three**. Written to the POSIX subset under a Bash shebang (§7.1), so it also runs under `dash`, `ash` and `brush` -- verify with `nix run nixpkgs#shellcheck -- -s sh scripts/rebuild-classic.sh`, which must stay at zero findings. Two behaviours differ by necessity: the Nushell `antigravity-status` and `flatpak-status` return records that other commands consume as data, whereas the script only prints; and the mcpctl drift probe needs `jaq` or `jq` for its filter expressions, so it is **skipped with a note** when neither is present rather than allowed to fail into a silently-wrong zero (the bundled `python3` fallback understands dotted paths only, which is all the antigravity probe needs).

Flags, shared by all three: `--dry` (dry-build, no cleanup/mirror; the git sync only reports), `--no-sync` (skip the git sync), `--branch <NAME>` / `-b` (switch to origin's branch first), `--no-update`, `--update-all` (`--full-update` in `preflight`; since 2026-10-10 every full run is already a bare `nix flake update` over **every** input -- stable `nixpkgs` and `home-manager` included, and any input added to `flake.nix` without an edit to the three implementations -- so in `rebuild` and `rebuild-classic.sh` the flag is kept only for compatibility; it still conflicts with `--no-update` and `--skills-only`; in `preflight` it implies `--update-vendored`, `--update-ai-tools`, `--update-appimages` (unless `--no-appimages` is given), and `--update-flatpaks` (unless `--no-flatpak` is given), because "update everything" that skips the pins `nix flake update` cannot move, or the AI tools installed outside Nix, leaves the stalest things behind), `--no-gc`, `--trace` (adds `--show-trace --verbose`), `--skills-only` (bump only `construct`; skip GC, the mirror and the mcpctl probe), `--no-flatpak` (skip a Flatpak update requested by `--full-update`), `--detach-flatpak` (request a Flatpak update and return instead of following its progress; conflicts with `--no-flatpak`). `preflight` adds `--update-appimages` and `--no-appimages` (see **AppImages** below), `--update-flatpaks` (update Flatpaks after a successful switch), `--no-commit` (see **Deps commit** below), `--reclaim` (reclaim safe caches before the switch; implied when `/nix` is low), `--gc-all` (`nix-collect-garbage -d` instead of keeping a week — no rollback), `--journal-days <DAYS>` (default 7), `--mcp-deploy` (deploy MCP host configs instead of only reporting drift), `--update-vendored` (run `pkgs/update-vendored.nu` after GC and before the switch -- after, because its `nix build --no-link` outputs are unrooted and a later GC would re-download them; `--check` under `--dry`; reports which pinned files changed, since the script always exits 0; conflicts with `--skills-only`), `--update-ai-tools` (after the switch, whether or not it succeeded, run the self-updater of each AI tool installed outside Nix (constraint #4), one at a time: `claude update`, `codex update`, `opencode upgrade`, `grok update`, `cursor-agent update`, `copilot update`, `kiro-cli update --non-interactive`, `goose update`, `agy update`, `omp update`, `pool update`, then `uv tool upgrade --all` and `npm update --global` (which also covers `kilo`, `mimo`, `kimi` and `qwen`: their own updaters could not update their curl installs, so they became npm globals on 2026-10-13; for globals npm's wanted version is `latest`, so majors move too). A tool installed with extras must record them in uv (`uv tool install llm --with llm-ollama`): an upgrade re-resolves from uv's record and drops anything added behind its back. The table is `pkgs/preflight/src/ai_tools.rs`; adding a tool is one line there. Each program is resolved by bare name on the PATH preflight inherits, so the out-of-band dirs decide; a tool that is not installed is skipped, and so is a self-updater that now resolves into `/nix/store`, since it would have to overwrite a store path. Every updater gets a null stdin, so a prompt reads EOF and declines rather than hanging, and its stdout goes to stderr, so `--json` keeps one payload; one that runs past 30 minutes is killed (the updater only, not any helper it spawned, which keeps Ctrl-C at the terminal reaching it). A failure is reported and the next tool still runs. `--dry` lists the commands instead; conflicts with `--skills-only`. First run, 2026-10-13: with a 10-minute cap, `omp update` and `uv tool upgrade --all` were killed mid-download on this link while every other tool finished well inside it, hence 30 minutes), and `--json` / `--format`.

**Deps commit (`preflight` only, 2026-10-24).** A run that bumped something now commits it right away instead of leaving `flake.lock` and the vendored pins modified in the checkout (constraint #53; `pkgs/preflight/src/deps_commit.rs`). The bumps are the lock, when the flake update succeeded and the lock differs from `HEAD`, and the files `--update-vendored` newly changed; a path already modified before the run is somebody's change and stays out. The step (`deps-commit`) runs after the `/etc/nixos` mirror and the mcpctl probe and before the AppImage check, and only when the switch succeeded, the run is not `--dry` or `--no-commit`, and `HEAD` is origin's default branch. When the lock moves `construct`, it first runs `nu pkgs/sync-skills.nu` so `.github/skills/` goes into the same commit (the Skills Drift check fails a lock bump without it). It then cuts `chore/deps-bump-<YYYY-MM-DD>` from `HEAD` (`-2`, `-3`, … when that name exists locally or on origin), runs `git add --all -- <paths>` and a plain `git commit -m 'chore(deps): bump flake inputs[ and vendored pins]' -- <paths>` — `--only` semantics, so anything else staged stays staged and out of it, and the user's own signing configuration applies (`gitway-add` loaded the key at the start) — and switches back to the default branch. Other uncommitted changes ride along both ways. Nothing is pushed; the step's line ends with the `git push -u origin <branch>` command. A failed commit switches back, deletes the empty branch and leaves the bumps in the tree; on another branch or a detached `HEAD` the step is skipped with a warning naming the paths. The trade-off of switching back: until the deps branch is merged, the checkout's lock is older than the running system, so a `--no-update` run in between builds the older lock. The Nushell `rebuild` and `rebuild-classic.sh` do not carry this; both are deprecated.

**AppImages (`preflight` only, 2026-10-21).** AppImages live outside Nix — Orca, Warp and WaveTerm sit in `~/Applications` and update themselves; BrowserOS is the exception, a pinned `appimageTools.wrapType2` that moves with `--update-vendored` — so no flake update reaches them. A routine rebuild leaves them alone. `--update-appimages` (or `--update-all` / `--full-update`, unless `--no-appimages` is given) asks **Gear Lever** (`it.mijorus.gearlever`, declared in `modules/packages/flatpak.nix`) for `--list-installed --json` and `--list-updates --json` (its versioned schema 1, Gear Lever 4.6 and later), records an `appimage-check` step, and only then applies updates with `flatpak run it.mijorus.gearlever --update --all --yes`. Each query is killed after five minutes, so a stalled source cannot hold the run. The check is delegated rather than written here because Gear Lever already reads both an AppImage's embedded update information (`gh-releases-zsync|…`, `zsync|<url>`) and the per-app sources a user sets (GitHub, GitLab, Codeberg, Forgejo, a static URL); a second implementation of zsync and six release APIs would only drift. Gear Lever only knows the AppImages it has integrated (its folder, `~/AppImages` by default), so `~/Applications` and `~/AppImages` are also scanned for `*.appimage` files it does not list; each is named with whether it embeds update information, read straight from its `.upd_info` ELF section (positioned reads of the header and section table only — an AppImage is often hundreds of MiB). One that embeds it gets a warning with the `--integrate` command that would bring it under the check; one without it is an info line (it updates itself, or by hand). Gear Lever skips an app that is running (it needs `--force` to replace one in use), and the run warns which those are. `--dry` lists the command instead. `preflight appimage status` (with `--json`) is the check on its own; it exits 3 (`NO_GEAR_LEVER`) without Gear Lever. The Nushell `rebuild` and `rebuild-classic.sh` do not carry this: both are deprecated, and the check is one Gear Lever command anyone can run by hand (`flatpak run it.mijorus.gearlever --list-updates`).

Measured cost of a prose-only skill change, so the flags can be chosen on evidence rather than feel: the skill derivation itself is **~0.6 s** (2.9 MB, 44 skills), a warm system eval is **~20 s** (the tree is usually dirty, so there is no eval cache at all), and the `/etc/nixos` no-op rsync is **~0.05 s** — not a cost worth gating on a diff. The expensive parts are the every-input `flake update` and the GC, which is exactly what `--skills-only` drops. `skills-sync` avoids the switch altogether.

Measured on the **download** side (2026-09-15), because that is what the flags are usually chosen to avoid: a stable `toplevel` built from a tree already on the current lock wanted **1.1 GiB (3.0 GiB unpacked) across 29 paths**, and all 29 derivations left to build were activation-layer glue — `system-path`, `etc`, `activate`, the unit/dbus/polkit wrappers — seconds, not minutes. The recurring download driver is **`nixpkgs-unstable` in the update list**, non-obviously so: `unstablePkgs` is threaded into the *stable* configuration (`uv`, `steam-run`, `code-cursor-fhs`, `kiro-fhs`), so every bump of it drags a second channel's closure in for those four. `--no-update` is the flag that costs nothing. Note that `--reclaim` and `--gc-all` free **disk** and *increase* the next fetch by discarding cached store paths — neither is a download remedy.
